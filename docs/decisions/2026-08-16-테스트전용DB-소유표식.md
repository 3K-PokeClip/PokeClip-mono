# ADR-0002: 통합 테스트는 전용 테스트 DB에서만 돌리고, 그 DB의 소유는 표식(marker table)으로 판정한다

날짜: 2026-08-16 / 상태: 확정 / 관련: POK-80, ADR-0001(이 저장소), ADR-030(아키텍처 저장소 — `stream_segments` 컬럼 변경은 3번 승인 필수), 계약-세그먼트인덱스

## Context

`media/internal/index`의 SQL 통합 테스트(실제 PostgreSQL에 붙어서 도는 테스트)는 두 파일로 나뉘어 있었고, **접속 대상이 서로 달랐다.**

- `upload_store_test.go` — 같은 서버에 전용 테스트 DB(`PG_TEST_DB`, 기본 `pokeclip_uploadtest`)를 만들어 그 안에서만 돌았다. 회차마다 표를 통째로 비우고 시작한다.
- `store_test.go` — `PG_DSN`(개발용 접속 문자열)이 가리키는 **공용 개발 DB에 직접** 행을 넣었다. 지우는 코드는 없었다.

그래서 `store_test.go`가 만든 `itest-<epoch>` 형태의 테스트 스트림 행이 공용 개발 DB에 **영구 누적**됐다. POK-30 조사에서 실제로 1,121행이 발견됐다 — 아무도 지우지 않았기 때문이다.

원 티켓(POK-80)의 처방은 "`t.Cleanup`(테스트 종료 시 실행되는 뒷정리 훅)에 삭제를 추가한다"였다. 즉 **더럽힌 뒤 치우는** 방향이다. 검토 중 사용자(kty)가 "store도 그 별도 DB에서 돌리면 되는 거 아냐?"를 제기했고, 확인 결과 `store_test.go`가 공용 DB에 붙어 얻는 검증 가치는 미미했다(그 테스트도 스키마를 자기가 `EnsureSchema`로 만들고, 공용 DB와는 같은 PG 서버 안에서 이름만 다를 뿐이다). 방향을 **접속 대상 분리**로 바꿔 사용자가 확정했다(`_workspace/00_clarifier_qa.md`).

전용 DB로 통일하자 새 위험이 하나 열렸다. 재실행을 지원하려면 `CREATE DATABASE`가 42P04(이미 존재한다는 PostgreSQL 오류 코드)를 정상으로 넘겨야 하는데, 그 관용은 "`PG_TEST_DB`가 **이미 존재하는 남의 DB**를 가리키는" 경우까지 함께 통과시킨다. 통과하면 그 DB의 표가 비워진다. 그래서 "이 DB를 채택해도 되는가"를 비우기 전에 판정해야 한다.

첫 처방은 "public 스키마의 표 개수·이름이 우리가 만든 모양과 같은가"였다. 검수 2라운드에서 **뚫렸다.** 이 저장소의 공용 개발 DB는 public에 `stream_segments` 하나뿐이라 우리가 만든 DB와 모양이 완전히 같다. 미끼 DB(`stream_segments` 1개 + 소중한 행 1개)로 실증했더니 그 행이 사라졌다.

## Decision

1. **`media/internal/index`의 모든 SQL 통합 테스트는 전용 테스트 DB에서만 돈다.** 접속·부트스트랩 코드는 신설 `testdb_test.go`의 `newTestPool` 하나로 모은다. `PG_DSN`은 `CREATE DATABASE` 한 문장을 내는 **관리 접속으로만** 쓰이고, 표에 대한 읽기·쓰기는 전부 전용 DB 안에서 일어난다.
2. **DB 소유는 모양이 아니라 표식으로 판정한다.** 새로 만든 DB 안에만 빈 표 `pokeclip_testdb_marker`(열 0개 — 존재 자체가 계약이라 담을 것이 없다)를 심는다. 42P04로 기존 DB를 채택할 때는 `to_regclass`로 이 표식이 있는지 확인하고, **없으면 표를 비우기 전에 즉시 실패**한다.
3. **부트스트랩 앞에 가드 2종을 더 둔다.** ① `PG_TEST_DB`가 `PG_DSN`의 DB 이름과 같으면 즉시 실패(그대로 두면 공용 DB가 비워진다). ② `PG_DSN`에 DB 이름이 없으면 즉시 실패(빈 값이면 서버가 롤 이름과 같은 DB를 골라 주므로 ①번 가드가 무력화된다).
4. **표식이 없는 기존 전용 DB는 1회 지우고 재실행한다.** 자동 채택하지 않는다.

## Alternatives Considered

**A. 표 개수·이름으로 채택 여부를 판정 (검수 2라운드까지의 처방)**
- Pros: 추가 객체를 만들지 않는다. 구현이 짧다.
- Cons: 이 저장소의 공용 개발 DB가 정확히 그 모양(public에 `stream_segments` 하나)이라 판정이 성립하지 않는다. 미끼 DB 실증에서 1행이 실제로 사라졌다. 또한 `ddl.go`에 표가 하나 늘 때마다 검사 조건을 함께 고쳐야 하는 이중 관리가 생긴다.
- Why not: **실증으로 뚫렸다.** 모양은 우연히 같을 수 있지만 표식은 우리가 심은 것만 존재한다.

**B. 원 티켓대로 `t.Cleanup`에서 `itest-%` 행을 지우기 (사후 청소)**
- Pros: 티켓 문언 그대로. 변경 범위가 가장 작다.
- Cons: 테스트가 패닉·SIGKILL·타임아웃으로 죽으면 `t.Cleanup`이 안 돈다 — 잔재가 다시 쌓인다. 공용 DB를 대상으로 하는 삭제 문장이 상시 리포에 남으므로, 접두사 조건이 언젠가 잘못되면 남의 데이터가 사라진다.
- Why not: 오염 경로를 남긴 채 확률만 낮춘다. 접속 대상을 나누면 오염 경로 자체가 0이 된다.

**C. 공용 DB에 상시 안전망 sweep(주기적 잔재 청소) 추가**
- Pros: 과거·미래 잔재를 모두 덮는다.
- Cons: B와 같은 이유로 공용 DB를 대상으로 하는 삭제 문장이 상시 상주한다. 그리고 전용 DB 통일안을 택하면 잔재가 생기는 경로가 없어 **청소할 대상 자체가 없다.**
- Why not: 불필요해져서 소멸했다(`00_clarifier_qa.md`에서 명시 기각). 과거 잔재는 1회 수동 SQL로 처리한다.

**D. 마커가 없고 표도 0개면 자동으로 마커를 심고 채택 (고아 DB 자동 복구)**
- Pros: 부트스트랩이 중단돼 마커 없는 빈 DB가 남았을 때 사람 손이 안 든다.
- Cons: "빈 DB는 남의 것이어도 채택한다"는 구멍이 차단면에 생긴다.
- Why not: 고아 DB는 구조상 항상 빈 DB이므로 안내된 수동 삭제가 무손실 복구다. 편의를 위해 차단면을 넓힐 이유가 없다.

## Consequences

- Positive: 공용 개발 DB의 `stream_segments`가 테스트로 오염되는 경로가 **구조적으로 0**이 된다(사후 청소가 아니라 접속 대상 분리). 잔재 sweep 코드가 불필요해져 `store_test.go`에서 44줄, `upload_store_test.go`에서 79줄이 삭제됐다(추가 9줄 — 순감 70줄). 표식 판정은 `ddl.go`와 무관하므로 표가 늘어도 검사를 고칠 필요가 없다(구 표-개수 검사였다면 격행 실패했을 시나리오를 실증으로 확인).
- Negative: `PG_DSN` 롤에 `CREATEDB` 권한이 필요하다(없으면 skip이 아니라 실패). 기존 로컬 전용 DB `pokeclip_uploadtest`는 표식이 없어 **1회 지우고 재실행**해야 한다. `ddl.go`를 바꾸면 전용 DB가 `CREATE TABLE IF NOT EXISTS` 때문에 옛 스키마를 유지하므로 역시 지우고 재실행해야 한다.
- 알려진 제약: 같은 `PG_TEST_DB`로 두 실행을 동시에 돌리면 서로의 데이터가 사라진다 — 두 문서에 "실행마다 고유한 `PG_TEST_DB`"를 규약으로 적었다. 동시 실행 시 마커를 심기 전 밀리초 창에서 상대 실행이 "남의 DB"로 오탐할 수 있다(같은 규약이 완화한다).
- 계약 무접촉: `stream_segments`의 DDL(`media/internal/index/ddl.go`)은 **0줄 변경**이다. ADR-030이 요구하는 3번 승인 절차에 걸리는 변경이 없다.
