# ADR-0003: media 컨테이너를 비특권 계정으로 돌리고, 볼륨 소유권은 이미지 층에 심는다

날짜: 2026-08-17 / 상태: 확정 / 관련: POK-79, POK-74(훅 점화 — 이 티켓의 발단),
ADR-031(아키텍처 저장소 — 실효 없는 조치 기각. **이 ADR이 그 결정의 이행이다**),
ADR-027(MediaMTX 훅 채택), ADR-021(수신부 네트워크 — 교체는 블루-그린 drain, 심리스 이전 비목표),
ADR-029(커밋·PR 프리픽스 폐기), ADR-0002(이 저장소 — 테스트 전용 DB)

## Context

POK-74로 MediaMTX가 **외부 명령(훅 기록 도구)을 실행하기 시작**했다. 보안 검수가 "사이드카에는
`no-new-privileges:true`가 있는데 media에는 없다"고 지적했고, 실측 결과 media는 **root로 돌면서
`/recordings`·`/dvr`·`/hooks`에 쓰기 권한을 갖고 있었다**.

ADR-031은 "플래그만 넣는 것은 **지금 막는 것이 0**이다(root는 이미 최상위이고 이미지에 setuid
파일이 0개다). 실효 없는 체크로 하드닝된 것처럼 보이게 하지 말고 **비특권 계정 전환과 묶어**
POK-79로 이관한다"고 결정했다. 이 ADR이 그 이행이다. (그 결정이 요구한 "README 제약표 기재"는
실측 결과 이행되지 않은 상태였고 — `no-new-privileges` 문자열은 리포 전체에서
`docker-compose.yml` 1곳뿐이었다 — 이 PR이 함께 해소한다.)

전환이 한 줄로 끝나지 않는 이유는 **볼륨 소유권**이다.

- Docker Engine은 named volume이 **비어 있을 때만** 이미지의 같은 경로에서 소유권·모드를
  복사한다. **이미지에 그 경로가 없으면** `populateVolume`이 `os.IsNotExist → return nil`로
  건너뛰고, 볼륨은 `0755 root:root`로 남는다 → 비root 쓰기 불가(moby `docker-v29.4.0` 기준,
  우리 Engine 29.4.0).
- 공식 이미지가 scratch 파생이라 **컨테이너 안에 셸이 없어 `chown`을 할 수 없고**,
  `/etc/passwd`도 없어 사용자 이름을 해석할 수단이 없다(이미지 내용물 파일 3개).

로컬 실험(E1~E8, Engine 29.4.0/arm64)으로 확인했다. E1 디렉토리 없는 이미지 + 새 볼륨 →
쓰기 거부 / E2 빈 디렉토리를 `COPY --chown`으로 넣으면 → 새 볼륨이 그 UID 소유로 생성 /
E3 볼륨 재생성 후에도 유지 / E4 **이미 비어있지 않은 볼륨은 안 고쳐진다** / E6 `COPY`는
디렉토리 mode를 보존하지 않고 `--chmod`도 디렉토리엔 안 먹는다(= setgid를 이미지에 심을 수
없다) / E7 `bluenviron/mediamtx:1.19.3`을 `-u 10002:10002`로 기동하면 정상, 전 리스너 up /
E8 **Docker Desktop은 bind mount 소유권을 컨테이너 UID로 재매핑한다**(= Mac에서 통과한 구성이
리눅스에서 깨질 수 있다).

## Decision

1. **media는 UID/GID 10002:10002로 돈다.** 실행 계정의 정본은 `media/Dockerfile.mtxhook`의
   `USER`다(사이드카 `media/Dockerfile`의 `USER 10001:10001`과 같은 관례). compose에는 정본
   위치를 가리키는 주석만 둔다 — 같은 값이 두 곳에 있으면 한쪽만 바뀐다.
2. **볼륨 소유권은 이미지 층에 심는다(C안).** `alpine:3` 기반 `prep` 스테이지에서 빈 디렉토리
   `/recordings`·`/dvr`·`/hooks`를 만들고 `COPY --chown=10002:10002 --from=prep`으로 최종
   이미지에 넣는다. 런타임에 소유권을 고치는 주체는 **존재하지 않는다.** `--chown`은 숫자만
   쓴다(`/etc/passwd` 부재).
3. **`security_opt: [no-new-privileges:true]`를 media에 붙인다.** 실행 계정이 낮아졌으므로 이제
   이 플래그가 막을 것이 생긴다 — ADR-031이 요구한 "실질 조치와 묶기"가 성립한다.
4. **사이드카와 다른 UID를 쓴다(10002 ≠ 10001).** 파일 교환은 소유권이 아니라 모드로 성립한다
   (녹화 0644·디렉토리 0755·스풀 0644 명시 chmod). 같게 두면 그 모드 계약이 **런타임에서
   관측 불가**가 된다 — 스풀이 0600으로 퇴화해도 스모크가 통과한다. 다르게 두면 스모크 자체가
   모드 계약의 실물 검사가 되고, "누가 쓴 파일인가"가 소유자로 드러난다.
5. **팀 전원이 1회 볼륨 3종을 초기화한다.** 기존 볼륨은 고쳐지지 않는다(E4).
   `down` → `docker volume rm pokeclip_{recordings,dvr,hooks}` → `up -d --build`를 한 덩어리로.
   **`down -v`는 금지**한다(`pgdata`까지 지워진다).
6. **회귀 장치를 둔다.** `media/internal/mtxhook/runtime_identity_contract_test.go`가
   Dockerfile의 `COPY --chown` 3줄·`USER`, `docker-compose.yml`의 `no-new-privileges`·볼륨 3종
   마운트·**활성 YAML의 복사 금지 옵션 부재**를 대조한다(주석 줄은 판정에서 제외한다 — 경고
   주석이 스스로를 실패시키면 안 된다. 꼬리 주석 절단만 기존 헬퍼의 관례이고 주석 줄 전체
   제거는 이 테스트가 새로 두는 규칙이다).
   - **대조는 문자열이 아니라 구조를 보고 한다.** Dockerfile은 **최종 스테이지만** 본다 —
     앞 스테이지의 `USER`·`COPY`는 최종 이미지가 물려받지 않으므로, 스테이지를 하나 덧붙이면
     단언이 전부 초록불인데 이미지는 root로 돈다(실측). 이 실패는 스모크로도 안 잡힌다:
     root는 10002 소유 볼륨에 그대로 쓰므로 녹화·훅·인덱싱이 전부 정상이고 보안 자세만
     조용히 사라진다. `COPY`는 목적지뿐 아니라 **소스(`/prep/<dir>`)까지** 대조한다 —
     소스가 파일이면 `/recordings`가 디렉토리가 아니게 되어 마운트가 깨진다.
     compose는 **부모 키 소속**을 들여쓰기로 확인한다 — 평탄 검색이면 `command:` 밑에 같은
     문자열을 적어 두는 것만으로 플래그도 마운트도 없이 통과한다(실측). 복사 금지 옵션은
     큰따옴표 스칼라의 `\uXXXX`·`\xXX` 이스케이프를 되돌린 뒤 찾는다. **완전한 YAML 파싱은
     하지 않는다**(의존을 늘리지 않는다는 관례) — `\UXXXXXXXX`(8자리)나 앵커·병합 키 같은
     **의도적 우회는 목표 밖**이고, 목표는 실수로 적어 넣은 표기를 잡는 것이다. 대소문자는
     내리지 않는다: compose의 `nocopy` 키는 대소문자를 구분해 `NoCopy`를 아예 거부하므로
     (실측 — `additional properties 'NoCopy' not allowed`) 소문자화는 막아 주는 것 없이
     정상 값만 오탐한다.
   - **훅 바이너리는 root 소유로 못박는다(단언 6).** `COPY --from`은 빌드 컨텍스트에서
     복사할 때와 달리 **소스 스테이지의 uid를 보존한다**(실측). 따라서 `--chown=0:0`이 없으면
     build 스테이지에 `USER`를 넣는 선의의 변경 하나로 `/hooks-bin/mtxhookwrite`가 10002 소유가
     되고, **실행 계정이 자기 훅 바이너리를 덮어쓸 수 있게 된다** — 그 불가능성이 아래 결정 7의
     전제다. Dockerfile에 `--chown=0:0`을 명시하고 계약 테스트가 그것을 요구한다.
7. **`read_only: true`는 넣지 않는다.** 두 종류의 이득을 나눠서 따진 결과다.
   - **침해 시 이득 = 0.** UID 전환 이후 루트FS에 10002가 쓸 수 있는 곳이 없다(이미지 내용물
     전수 검사: 파일 3개 + `/hooks-bin`, 전부 root 0755. scratch 파생이라 `/tmp`조차 없다).
     RCE를 가정해도 공격자는 10002로 **세 볼륨에** 쓸 수 있고 `read_only`는 그것을 막지 못한다.
   - **오설정 관측 이득은 0이 아니다(실측 정정).** 볼륨 마운트가 빠진 채로 뜨면, `read_only`가
     있을 때는 `mkdir /recordings/<path>: read-only file system`으로 **즉시 시끄럽게** 죽고,
     없을 때는 조용히 컨테이너 쓰기 층에 쌓인다(`docker diff`에 mp4가 실제로 보인다).
     그래서 "추가로 막는 것이 0"이라는 서술은 틀렸다 — 이 이득은 존재한다.
   - **그럼에도 넣지 않는 이유**: 그 오설정은 계약 테스트 5번(마운트 단언)이 더 이르고 더
     정확하게 잡는다. **단 그 테스트의 사각을 알고 택한 것이다** — CI 시점에 `docker-compose.yml`
     **한 파일만** 보므로 개인 override·수동 `docker run`·K8s 매니페스트 경로는 잡지 못한다.
     그 경로들에서는 이 방어가 없다.
   - **최종 방향과의 정합**: K8s 절의 매니페스트는 두 컨테이너 모두 `readOnlyRootFilesystem: true`를
     켠다. 즉 이 결정은 "영구 기각"이 아니라 **compose 단계에서의 보류**이고, 위 사각(수동 실행·
     매니페스트 경로)이 실제 운영 경로가 되는 K8s 전환 시점이 곧 재평가 시점이다.

## Alternatives Considered

수집 34건 + 독립 평가(실험 E1~E8)로 7개 안을 채점했다
(근거 강도 40 / 우리 제약 적합 40 / 유지보수·전환 비용 20).

**C. 이미지에 디렉토리 심기 — 88점 (채택)**
- Pros: 런타임 root 개입 0 · 도구 버전 비의존(Compose 5.1.2에서 그대로 동작 — Engine 동작이지
  Compose 기능이 아니다) · 볼륨 재생성 후 자동 재적용(E3) · `build:`를 이미 쓰고 있어 추가
  비용이 Dockerfile 6줄 · 대형 선례(Grafana의 GF_UID 패턴)
- Cons: 기존 볼륨을 고치지 못한다(E4) → 1회 초기화 마찰 · 트릭이 비직관적 · 이 동작이 Docker
  공식 문서에 없다(정본이 코드라 무고지 변경 위험)
- Why: 완료 조건을 end-to-end로 실증한 유일한 안이고, 프로덕션 신규 환경에서는 유일한
  약점(기존 볼륨)이 성립하지 않는다.

**B. 별도 init 서비스 + `service_completed_successfully` — 83점 (보완용)**
- Pros: 적합도 최고(36/40) — 5.1.2에서 동작하고 **기존 볼륨까지 고치는 유일한 안**
- Cons: 서비스가 영구적으로 하나 늘고, **매 `up`마다 root 컨테이너가 우리 볼륨에 rw로 붙는다**
  (보안 자세로는 후퇴). `docker compose ps` 노이즈와 부팅 지연
- Why not: 1회 초기화로 대체 가능한 이득을 위해 상시 root 컨테이너를 남길 이유가 없다.

**A. Compose `pre_start` + busybox chown — 71점**
- Pros: 가장 선언적. 스펙·구현·PR을 1차로 확인했고 완료 조건도 충족한다
- Cons: **Compose ≥5.3.0 강제**(로컬 실측 5.1.2, Docker Desktop ≥4.82.0) — 팀 3명 + 배포
  환경이 전부 올려야 한다. `git pull && docker compose up -d --build` 하나로 재현된다는 제약을
  정면으로 깬다. 출시 6주차 기능이고 `bluenviron/mediamtx` + `pre_start` 공개 선례 0건.
  훅 컨테이너에는 `security_opt`가 전달되지 않아 **no-new-privileges 없는 root 컨테이너가
  매 재생성마다 볼륨을 만진다**
- Why not: 도구 버전 강제가 결정타. 스펙과 구현의 재실행 조건도 어긋난다.

**D. root 유지 + gosu식 강등 — 56점**
- Pros: postgres 공식 이미지의 검증된 패턴
- Cons: ENTRYPOINT를 갈아끼워야 하고 **컨테이너가 root로 시작**한다 — 목표와 배타적
- Why not: 목표 훼손.

**공용 GID(`group_add`) — 54점**
- Pros: compose 스펙이 정확히 이 유스케이스를 예로 든다
- Cons: 우리 요구는 "사이드카가 `:ro`로 읽기"뿐이고 0644로 이미 성립한다. 그룹 쓰기가
  필요해지면 Docker에 umask 수단이 없고, **setgid를 이미지에 심을 수단도 없다**(E6)
- Why not: 효과 없는 복잡도만 는다. **단 K8s에서는 정답으로 승격된다**(아래 절).

**E. userns-remap — 42점**: daemon.json 전역 설정 = compose only 위반 + 머신마다 설정.
**F. tmpfs `driver_opts o=uid=` — 36점**: 비영속. 녹화·DVR·스풀과 정면 충돌.
**bind mount 전환**: Docker Desktop만 소유권을 재매핑하므로(E8) **Mac에서 통과하고 리눅스에서
깨진다.** 로컬은 named volume을 유지한다. 배포 환경에서 bind mount를 택한다면 C안 대신 호스트
측 소유권 준비가 정답이 되며, 그 판단은 배포 설계 시점에 한다 — 반드시 리눅스에서 실측할 것.
**MediaMTX 설정으로 우회**: `recordPath`/`hlsDirectory`를 어떻게 잡아도 MediaMTX는 볼륨 마운트
지점 자신에 디렉토리를 만들어야 하므로 성립하지 않는다.

## Consequences

- Positive — **가장 큰 실질 이득은 훅 바이너리가 서버의 사정권 밖으로 나갔다는 것이다.**
  `/hooks-bin/mtxhookwrite`는 `root:root 0755`로 남고, 10002는 그것을 **실행만 할 수 있고
  덮어쓸 수 없다**(실측: 10002로 그 경로에 쓰면 `permission denied`, 실행은 성공).
  이 티켓의 발단이 "POK-74로 MediaMTX가 **외부 명령을 실행하기 시작했다**"인 만큼 이것이 핵심이다 —
  서버가 root이던 동안에는 서버가 그 명령 자체를 바꿔 칠 수 있었고, 이제는 아니다.
  그 위에서 `no-new-privileges`가 권한 되찾기 경로를 막는다(ADR-031의 비대칭 해소).
  나머지: 침해 시 할 수 있는 일이 "10002가 세 볼륨에 쓴다"로 줄고, 런타임 root 개입이 0이며
  소유권이 이미지에 박혀 배포되므로 불변 인프라 원칙에 맞는다. 볼륨을 지우고 다시 만들어도
  자동 복원된다(수동 chown 0회).
- Negative: 팀 3명이 **1회** 볼륨 초기화를 해야 하고, 그 과정에서 로컬 녹화·DVR·스풀이
  지워진다(테스트 산출물뿐. 단 S3 업로더를 켜 둔 사람은 미업로드 `pending` 잔여를 먼저
  확인해야 한다). "빈 디렉토리를 COPY한다"는 비직관적 코드가 남는다 — 주석과 계약 테스트가
  그 이유를 지킨다.
- 알려진 제약:
  - 볼륨에 복사 금지 옵션(`volume.nocopy`)이 붙으면 이 해법이 **조용히** 무력화된다.
    주석과 계약 테스트로 봉인했으나, 개인 override 파일은 gitignore라 검사할 수 없다.
  - 비root 전환으로 **새 버전 의존 전제가 하나 늘었다**: "MediaMTX가 루트FS·CWD에 쓰지 않는다."
    우리 설정은 `moq: no`라 참이지만 `moq`/`webrtc`/`rtsps`를 켜며 `auto.key`류를 쓰면 비root에서
    실패한다(E7). `media/README.md`의 버전 전제 목록에 8번째로 등재했다(닻:
    `USER 10002:10002`). 전제 개수 표기가 8자리에 흩어져 있고 **그 드리프트를 잡는 자동 장치는
    없다** — 사람이 전수 확인한다.
  - 리눅스에서는 bind mount된 `/mediamtx.yml`의 호스트 모드가 그대로 보인다. 체크아웃 umask가
    0077이면 비root가 설정을 못 읽고 **기동 실패**한다(Mac에서는 재매핑 때문에 재현되지 않는다).
    처방은 `chmod a+r`.
  - MediaMTX v1.19.3의 HLS 서버는 최초 `index.m3u8` 요청에 **302**를 돌려준다. 검증 스크립트는
    `curl -sfL` + 쿠키 보존을 쓰고, 본문이 비지 않았는지까지 확인해야 한다.
- 롤백: **`git revert -m 1 <merge-sha>`** + `docker compose up -d --build`가 전부다(팀 머지
  방식이 merge commit이라 `-m 1`이 없으면 revert가 아무것도 하지 않고 종료한다). 되돌리면
  media가 다시 root로 돌고, root는 10002 소유 디렉토리에도 쓸 수 있으므로 **볼륨 재초기화가
  필요 없다.** 이 성질은 **격리된 임시 worktree**에서 리허설로 실증했다(작업 워크트리를
  건드리는 `checkout`/`reset --hard` 방식은 미커밋 편집을 복구 불가하게 지우므로 쓰지 않는다).
- 계약 무접촉: `infra/compose/mediamtx.yml` 0줄 변경, Go 프로덕션 코드 0줄 변경(주석 1곳의 사실
  정정 제외). `stream_segments` DDL 무접촉이므로 ADR-030의 3번 승인 절차에 걸리는 변경이 없다.

## K8s 전환 시 폐기·대체 가이드

> 이 해법은 **한시적**이다. K8s로 옮기면 플랫폼 기능이 같은 일을 하므로 지운다.
> 이 절은 그때 이 코드를 처음 보는 사람을 위한 것이다.

### 왜 폐기되는가

C안은 "moby가 빈 볼륨에 한해 이미지에서 소유권을 복사한다"는 **Docker Engine 고유 동작**에
기댄다. K8s에는 그 동작이 없고, 볼륨 마운트 시점에 소유권이 조정된다.
Kubernetes API 원문(`core/v1/types.go`, `PodSecurityContext.FSGroup`):

> "Some volume types allow the Kubelet to change the ownership of that volume to be owned by
> the pod: 1. The owning GID will be the FSGroup 2. The setgid bit is set (new files created
> in the volume will be owned by FSGroup) 3. The permission bits are OR'd with rw-rw----
> If unset, the Kubelet will not modify the ownership and permissions of any volume."

원문이 "**Some volume types**"라고 적은 대로 **모든 볼륨을 kubelet이 직접 바꾸는 것은 아니다** —
CSI 드라이버가 `VOLUME_MOUNT_GROUP` 능력으로 처리하는 경로도 있고 지원되지 않는 타입도 있다.
중요한 것은 **setgid까지 세운다**는 점이다. 그것은 우리가 이미지에 심을 수 없다고 실측한
바로 그 비트이고, 공용 GID를 기각한 유일한 이유였다.

**두 필드를 혼동하지 말 것.** 같은 파일의 `fsGroupChangePolicy` 주석은 이렇게 말한다:

> "…This field will only apply to volume types which support fsGroup based ownership(and
> permissions). It will have no effect on ephemeral volume types such as: secret, configmaps
> and emptydir."

이것은 **정책 선택(`Always` vs `OnRootMismatch`)이 그 타입들에는 의미가 없다**는 뜻이지,
**`fsGroup` 자체가 적용되지 않는다는 뜻이 아니다.** ConfigMap 볼륨 플러그인이 실제로
`FsGroup`으로 권한을 바꾼다는 반대 지적이 있으며, **우리는 실측하지 않았다 — 미확인이다.**
`OnRootMismatch`는 "지연을 항상 피한다"가 아니라 **볼륨 루트의 소유권·권한이 기대값과
일치하면 재귀 변경을 건너뛴다**는 뜻이다(시간 단축에 도움이 될 수 있다. 기본값은 `Always`).

근본적으로 Engine이 containerd/CRI로 바뀌면 이 결정의 근거 사슬 전체가 무관해진다.

### 대체 매니페스트 형태 — 한 파드 2컨테이너, `fsGroup`은 파드 레벨 단일 필드

검증된 참조는 `xunholy/k8s-gitops`(stars 640, Apache-2.0)다. **MediaMTX 1.19.3을 digest까지
pin**한 상태로 완전 비특권 구성을 운영한다(그 digest는 우리가 레지스트리에서 실측한 index
digest와 완전히 일치한다). 다만 **그 참조는 단일 컨테이너**라 `runAsUser`·`runAsGroup`을
파드 레벨에 몰아 넣었다. **우리는 두 컨테이너의 UID가 다르므로 그 둘을 컨테이너 레벨로
내린다.**

**⚠️ 아래는 보안 컨텍스트만 보이려고 발췌한 스니펫이다 — `spec.volumes`(PVC·ConfigMap 볼륨
정의)를 일부러 생략했다.** 그대로 복사하면 `volumeMounts`가 가리킬 볼륨이 없어 검증에서 거부된다.
볼륨 소스는 아래 "볼륨 모델"·"hostPath 금지" 절의 결론(PVC + ConfigMap)에 따라 그때 채운다.

    spec:
      # 파드 레벨 — fsGroup 은 PodSecurityContext 의 파드 단위 단일 필드다.
      # 컨테이너 securityContext 에는 존재하지 않는다(적으면 검증에서 거부되거나
      # 프루닝 툴체인에서 조용히 사라진다).
      securityContext:
        runAsNonRoot: true
        fsGroup: 10002
        fsGroupChangePolicy: OnRootMismatch
      containers:
        - name: media
          securityContext:
            runAsUser: 10002
            runAsGroup: 10002
            allowPrivilegeEscalation: false      # = compose 의 no-new-privileges:true
            readOnlyRootFilesystem: true         # "그때 다시 볼 것" 참조
            capabilities: { drop: ["ALL"] }
            seccompProfile: { type: RuntimeDefault }
          volumeMounts:
            - { name: recordings, mountPath: /recordings }
            - { name: dvr,        mountPath: /dvr }
            - { name: hooks,      mountPath: /hooks }
        - name: segment-indexer
          securityContext:
            runAsUser: 10001
            runAsGroup: 10001
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
            seccompProfile: { type: RuntimeDefault }
          volumeMounts:
            - { name: recordings, mountPath: /recordings, readOnly: true }
            - { name: hooks,      mountPath: /hooks,      readOnly: true }
      # volumes: 생략 — 위 경고 참조. recordings·dvr·hooks 는 PVC,
      #          mediamtx.yml 은 ConfigMap(defaultMode 명시)으로 간다.

**왜 한 파드인가**: `fsGroup`이 파드 단위이므로 두 컨테이너가 같은 보조 그룹 10002를 갖는다 →
사이드카(UID 10001)가 media(UID 10002)가 만든 파일을 **그룹으로** 읽는다. 이것이 UID 분리
설계가 K8s에서 성립하는 기전이다. **다른 파드로 분리하면 두 파드가 같은 볼륨을 공유해야 하고,
그것은 아래 "볼륨 모델"의 비공유 전제(교체 단위 사이)와 충돌한다.**

**한계**: 참조의 설정 주석은 `# Ingest + relay only — no recording, no transcoding.`이다.
**볼륨 쓰기 경로는 검증하지 못한다.**

### 무엇을 지우고 무엇을 남기나

지운다: `prep` 스테이지 · `COPY --chown` 3줄 · 계약 테스트의 소유권/복사금지/마운트 단언 ·
compose `security_opt`(→ 컨테이너 `securityContext`로 이동).

**남긴다 — `USER 10002:10002`(숫자).** 근거는 둘이다.
(1) **매니페스트 누락에 대한 심층 방어.** kubelet은 `runAsUser`가 명시되면 그 값으로
`runAsNonRoot`를 판정하고, 명시되지 않았을 때 이미지의 사용자를 본다. 따라서 "이미지가 root면
무조건 파드 거부"는 **틀린 서술이다** — 남기는 값은 "컨테이너에서 `runAsUser`를 빠뜨려도
root로 떨어지지 않는다"는 보험이다.
(2) **K8s 밖에서도 비root가 유지된다** — 디버그 `docker run`, CI, 로컬 재현.
덧붙여 숫자 UID면 사용자 이름 해석이라는 변수 자체가 없다(이 이미지에는 `/etc/passwd`가 없다).
kubelet의 이름 해석 기전 자체는 미확인이므로 근거로 세우지 않는다.

함께 남긴다: 계약 테스트의 `USER` 단언 · **훅 바이너리 소유 단언(6 — 오케스트레이터와 무관하게 성립한다)** · 0644/0755 모드 계약 · **UID 분리 설계**. `fsGroup`은
권한을 `rw-rw----`와 OR하므로 그룹 읽기·쓰기는 보장하지만 **other 읽기는 보장하지 않는다** —
교환의 근거가 "other 읽기"에서 "파드 공용 fsGroup 그룹 읽기"로 바뀐다. 그 순간 **공용 GID가
정답으로 승격된다.**

### 볼륨 모델과 블루/그린 제약

**결론의 근거는 접근 모드가 아니라 우리 설계다.** `ReadWriteOnce`는 "한 노드" 제한이며 같은
노드의 여러 파드는 공유할 수 있다(단일 파드 제한은 `ReadWriteOncePod`). 교체 단위마다 자기
볼륨을 갖는 이유는 그 제약이 아니라 **우리 설계가 교체 단위 사이의 볼륨 공유를 요구하지 않기
때문**이다 — 로컬 볼륨은 핫 창이고, 영속은 S3이며, 진실원은 PG 인덱스다(S3 LIST 금지). 이것은
**ADR-021의 "교체 = 블루-그린 버튼(drain/force), 심리스 이전 비목표"와 정합**한다.
(한 파드 안의 media↔사이드카 공유는 이와 다른 층이다.)
*(EBS/CSI 접근 모드는 이번 조사 범위 밖이다 — **출처 없음/미확인**. 전환 시 1차 문서로
재확인할 것.)*

**워크로드 형태는 배포 설계 시점 결정이다.** StatefulSet + `volumeClaimTemplates`는 후보 중
하나이지 정석이 아니다 — 안정 네트워크 ID·ordinal 보장은 우리 요구에 없다.

**그때 반드시 설계할 것(현재 미설계)**: drain 시점에 아직 업로드되지 않은 `pending` 세그먼트가
옛 볼륨에 남는다. **"`pending` 0 확인 → 볼륨 회수" 순서를 강제**해야 유실이 없다.

### hostPath 금지

`hostPath`는 **노드 로컬 경로에 묶여** 스케줄링을 깨고 노드 교체 시 데이터가 사라진다(PSS
baseline/restricted에서도 사실상 금지). **named volume → PVC**가 개념적으로 더 가까운
대응이다. `/mediamtx.yml`은 **ConfigMap 마운트**로 간다 — "호스트 umask 0077로 설정을 못 읽는"
위험이 소멸한다. 주의 둘: ① `defaultMode`를 0600으로 잘못 주면 재발하므로 값을 명시할 것(기본
0644). ② ConfigMap 볼륨에 `fsGroup`이 적용되는지는 **미확인**이다 — 어느 쪽이든 모드로
해결하는 편이 안전하다.

### 그때 다시 볼 것

1. **`readOnlyRootFilesystem`** — 이번엔 "UID 전환 후 막는 것이 0"으로 기각했으나, 참조가 실제로
   켜고 운영 중이고 **정책·보안 체크리스트가 요구할 수 있다**(내장 PSS restricted 프로필이 이
   필드를 요구하지는 않는다). 기준은 이번과 같다: **무엇을 막는가.**
2. **버전 전제 8번째(CWD 쓰기 없음, 닻 `USER 10002:10002`)** — `readOnlyRootFilesystem`을 켜면 이
   전제가 강제된다. `moq`/`webrtc`를 켜면 즉시 기동 실패한다. 표준 처방인 `/tmp` emptyDir을 쓸
   경우 **그 emptyDir의 소유권이 어떻게 결정되는지는 미확인**이다. 실측하고 결정할 것.
3. **공용 GID 승격**(위).
4. **버전 드리프트 장치** — `TestPinnedMediaMTXVersionMatchesDockerfile`은 그때도 살아 있어야
   한다. 이미지 참조가 매니페스트로 옮겨가면 대조 대상을 함께 옮긴다. 지우지 말 것 — 훅
   실패는 무징후다.

### 폐기 판정 체크리스트

위 **한 파드 2컨테이너 모델**을 전제로 한다. 아래가 **전부 실측으로 참**일 때만 "지운다"
목록을 실행한다. 설정에 그렇게 적혀 있다는 것은 근거가 아니다.

- [ ] 파드 레벨 `kubectl get pod <pod> -o jsonpath='{.spec.securityContext.fsGroup}'` = `10002`
- [ ] 컨테이너 레벨 `...'{.spec.containers[*].securityContext.runAsUser}'` = `10002 10001`
- [ ] **새로 만든 볼륨**에서 송출 1회 후 녹화 파일의 그룹이 `10002`
- [ ] `/hooks/events.jsonl`에 `online`·`segcomplete`·`offline` 3종이 쌓이고 그룹이 `10002`
- [ ] 사이드카 컨테이너의 `readOnly: true` 마운트에서 `reason:5` 존재 + `hook_line_invalid`
      계열 0건
- [ ] **볼륨을 지우고 다시 만든 뒤에도** 위 5항이 성립

**서두를 필요 없다.** C안은 K8s에서도 무해하다 — 이미지에 빈 디렉토리가 셋 있는 것뿐이고
`fsGroup`이 그 위에 덮어쓴다. 두 장치가 충돌하지 않으므로 실측을 끝낸 뒤에 지우면 된다.
먼저 지우고 실패하면 되돌릴 것이 없다.
**판정 실패 시**: 해당 볼륨 타입에 `fsGroup`이 적용되는지, CSI 드라이버가 그 능력을 광고하는지
부터 확인한다(미확인 항목). 그래도 안 되면 C안을 유지한다 — 유지 비용은 Dockerfile 6줄이고,
그 6줄이 왜 있는지는 이 문서가 설명한다.
