# dev-media — 계정별 방송 서버

> **상태:** 이 문서는 목표 구성(계정별 방송)을 설명한다. 지금 상자에는 아직 옛
> 공용 passphrase 판이 돌고 있고, 이 구성은 박스 반영 단계에서 올린다. 그 전에는
> 상자의 실물이 이 문서와 다르다.
>
> **미확인 — 10단계 실제 송출에서 확인:** 포크 `.2` 가 HTTP 인증이 돌려준
> passphrase 로 그 연결을 판정하는지(U 계약 — 설계 r1.7.4 2-1 A1–A7), 같은 토큰의
> 둘째 연결, 「양보 사슬」(아래 한계)은 로컬 실측을 하지 못했다. 아래의 판정 설명은
> 설계상 동작이다.

팀 dev 환경에서 가입한 스트리머가 자기 계정으로 OBS 송출을 하는 상시 서버다.
OBS 가 SRT[^srt]로 송출하면 MediaMTX 가 연결마다 그 계정의 passphrase(SRT 암호)를
auth 서비스에 물어 판정하고(설계상 — 미확인, 위 상태), 받은 방송을 LL-HLS 로 되감기 1시간과 함께 재생한다.
팀 공용 로컬 환경(`docker-compose.yml` · `infra/compose/`)과 수명이 다르므로 섞지
않는다. 담당은 CODEOWNERS 의 `/infra/`(1번)다.

*   **무엇이 바뀌었나:** 예전 판은 경로 하나와 공용 passphrase 하나로 데모 한
    방송만 받았다. 이 판은 계정 수와 무관하다. 계정을 더해도 설정 파일을 고치지
    않는다(설계 r1.7.4 1절 G1 · G7).
*   **왜 자체 재생 페이지인가:** MediaMTX 내장 플레이어는 일시정지 뒤 재생하면
    라이브 위치로 강제 점프해 되감기가 성립하지 않는다(2026-08-18 조사).
    `player.html` · `nginx.conf` 는 이 판에서 바뀌지 않는다.

이 구성이 팀 결정에서 벗어난 점(퍼블릭 서브넷 직노출 등)과 그 조건은
[**ADR-040**](https://github.com/3K-PokeClip/PokeClip-LLM-WIKI/blob/main/adr/ADR-040_%EC%9E%84%EC%8B%9C%EB%8D%B0%EB%AA%A8-media%EC%84%9C%EB%B2%84-%EA%B8%B0%ED%95%9C%EB%B6%80%EC%98%88%EC%99%B8.md)
에 기록돼 있다. 계정별 방송 판의 추기는 반영 뒤 기록 단계에서 더한다.

## 구성도

```text
 OBS (가입한 스트리머)
   │  SRT udp/8890   streamid=#!::r=<토큰>,m=publish · 그 계정의 passphrase
   ▼
┌─ dev-media 상자 (EC2 한 대, 퍼블릭 서브넷) ─────────────────────────────┐
│                                                                        │
│  mediamtx ── LL-HLS 먹싱 ── /dvr (세그먼트 900개 = 1시간)               │
│    │ ▲ 8888 (내부 전용)                                                 │
│    │ │ proxy_pass                                                       │
│    │ edge (nginx) ── /player.html 정적 서빙                             │
│    │   ▲ tcp/8888 ← 밖에 열리는 유일한 TCP 포트                          │
│    │                                                                    │
│    │ 제어망 mtx-control (10.250.0.0/29, internal — edge 는 붙지 않음)    │
│    ├── 인증 요청(publish · api) ──▶ ingest-auth (응답기)                │
│    ◀── Control API(긴급 절단) ──────┘      │                            │
│                                            │ 4C resolve (VPC 사설망)     │
└────────────────────────────────────────────┼────────────────────────────┘
     보안 그룹: udp/8890 · tcp/8888 을 팀 공인 IP/32 에서만 허용  │
   브라우저 http://<상자 주소>:8888/player.html?p=<토큰>           ▼
                                                    auth (dev EC2 :8082)
```

*   **mediamtx** — 포크 이미지 `v1.21.2-pokeclip.1`(계정 ECR — 핀은 `compose.yml`,
    레지스트리 호스트는 상자 `.env` 의 `MTX_IMAGE_REGISTRY`). SRT 송출을 받아 LL-HLS 로
    먹싱한다. UID 10002 로 돈다.
*   **ingest-auth(응답기)** — MediaMTX 의 HTTP 인증에 답하는 작은 서버다
    (`media/cmd/ingest-auth`, 이미지는 `media/Dockerfile.ingest-auth`). 연결마다
    auth 의 4C resolve(스트림키 해석 내부 API — 계약4 2절)로 토큰을 풀어 그 계정의
    passphrase 를 돌려준다. UID 10003 · 읽기 전용 루트로 돈다.
*   **edge(nginx)** — 재생 페이지와 HLS 프록시. 기본 망에만 붙는다.
*   **제어망** — MediaMTX 와 응답기 사이 인증 훅 · Control API 전용 망이다.
    밖으로 나가지 않는다(`internal`). 고정 주소는 `compose.yml` 과 템플릿이 같아야
    한다.

## 접근 통제

송출(publish)은 네 겹으로 막는다.

1.  **보안 그룹(IP/32).** SRT · 재생 포트를 팀 공인 IP 에서만 연다. 이 판에서
    바꾸지 않는다.
1.  **토큰 꼴 경로 하나.** 경로는 정규식 `~^[0-9A-HJKMNP-TV-Z]{26}$`(26자
    Crockford 문자셋) 하나뿐이다. 그 밖의 이름은 인증 전에 「path not
    configured」로 거부된다. 경로 이름 = 송출 토큰[^token]이고, 토큰은 비밀이 아니다.
1.  **계정별 passphrase.** MediaMTX 가 publish 연결마다 응답기에 묻고, 응답기가
    auth 에서 그 토큰의 passphrase 를 받아 돌려준다. MediaMTX 는 그 값으로 그
    연결의 SRT 암호를 판정한다(설계상 — 미확인, 위 상태). 비밀은 auth 쪽(Secrets Manager)에만 있고, 이
    디렉터리 · `.env` · 설정 파일 어디에도 없다.
1.  **경로 잠금값.** 렌더할 때마다 새로 만드는 64자 값을 경로 기본값의 송출 칸에
    둔다. 응답기가 값 없이 허용하면 이 값으로 판정돼 거부된다(빈 passphrase 의
    무암호 송출을 막는다). 값은 렌더 산출물에만 있고 아무도 알 필요가 없다.

재생 쪽은 이렇다.

*   **HLS 재생은 판정하지 않는다.** 읽기 통제는 계약3 서명 쿠키 몫이다.
    `authHTTPExclude` 는 read 한 줄뿐이다.
*   **SRT 읽기는 경로 잠금값으로 막는다.** 경로 이름이 공개 토큰이므로 막지
    않으면 누구나 원 스트림을 무암호로 읽는다. 그래서 같은 잠금값을
    `srtReadPassphrase` 칸에도 둔다. HLS 는 영향이 없다(설계 r1.7.4 2-8).
*   **Control API** 는 제어망 주소에만 묶고 호스트 포트에 내지 않는다. api 요청도
    응답기가 출발지와 자격으로 판정한다.

`render.sh` 가 렌더 결과에서 이 전제(`authMethod: http` · read 한 줄의 제외 ·
빈 `apiTrustedProxies` · 정규식 경로 · 잠금값 두 칸)를 단언한다. 하나라도 빠지면
산출물을 남기지 않는다.

## 운영 원칙

*   **판정을 못 하면 닫는다(fail-closed).** auth · 응답기 · 허용 연결 기록 · 거부
    목록 가운데 하나라도 판정하지 못하면 새 연결을 거부한다. 진행 중 송출은 인증이
    접속 때 한 번뿐이라 영향이 없다. 거부된 송출은 OBS 플러그인의 재시도가 다시
    붙인다(끊긴 뒤 300초까지 5초 간격, 그 뒤 30 · 60초 간격, 65분에 포기).
*   **응답기는 auth 를 부르는 시간을 묶는다.** 판정 불가로 끝난 토큰은 기억해
    4초에 하나만 다시 묻는다(실패 토큰 차례). 그래서 auth 가 느려도 MediaMTX 안의
    인증 처리 줄(경로 관리자 — 인증 · 등록 · 새 시청 세션을 한 줄로 처리한다)이
    쌓이지 않는다(설계 r1.7.4 3-8).
*   **동시 송출 상한은 Q-f 결정을 따른다.** 반영은 지금 상자와 팀 보안 그룹으로
    한다(소수 송출). 30명을 받기 전에 상자 사양 · 디스크 · DVR 창과, 팀 밖
    송출자라면 S1 게이트(인증 전 부하 방어 — IP별 한도)를 따로 정한다(설계 r1.7.4
    8-3 Q-f · 8-2 4).
*   **비밀은 명령 인자 · 로그 · 저장소에 싣지 않는다.** `.env` 는 상자에만 두고
    (root:root 0600) 값 주입은 RUNBOOK 의 「값 주입」 절대로 한다. 토큰은 공개
    식별자라 명령 인자에 실어도 된다.
*   **설정값의 정본은 아래 파일이다.** 세그먼트 길이 · DVR 개수 · 포트 · 주소는
    아래 파일들이 정한다. 이 문서(구성도 포함)와 RUNBOOK 에 적힌 값은 설명용이고,
    다르면 파일이 맞다.
*   **상태 디렉터리 · 세대 파일은 손으로 지우거나 옮기지 않는다.** 응답기의 허용
    연결 기록(`${DEMO_HOME}/ingest-auth/state`)은 긴급 절단의 근거다.

## 운영 순서

*   **MediaMTX 를 (다시) 띄우기 전에 응답기가 healthy[^healthy] 인지 본다.**
    응답기가 답하지 못하면 새 연결이 모두 거부되고, MediaMTX 의 인증 요청 하나가
    응답기 모양에 따라 곧바로 끝나거나 최대 10초를 붙잡아 줄이 쌓인다(갈래별 값은
    RUNBOOK 의 「운영 순서」 절).
*   **응답기 고장은 응답기를 먼저 살려 푼다.** MediaMTX 재시작으로 풀지 않는다 —
    진행 중 송출까지 끊겨 한꺼번에 다시 붙으며 같은 줄을 스스로 만든다.
*   **MediaMTX 재시작은 최후 수단이고 한 번만 쓴다(되풀이 금지).** 진행 중 송출이
    모두 끊긴다. 쓰는 때는 Control API 가 응답하지 않을 때, 그리고 긴급 절단의
    `cut` 이 끝까지 끊지 못했을 때(Control API 판 불일치 · cut 의 내부 오류(분류
    밖 결과) · MediaMTX 쪽 임시 포트 고갈로 거듭된 인증 실패)다. 유출 키의 진행 중
    송출을 바로 끊는 수단은 이것뿐이다. 갈래별 처방은 RUNBOOK 의 「긴급 절단」
    절이다.
*   `compose.yml` 의 `depends_on` 은 `up` 의 시작 순서(응답기 먼저)만 맞춘다.
    건강 조건은 걸지 않는다 — 응답기가 unhealthy 여도 MediaMTX 는 떠 있어야 한다.
    상자 재부팅 때는 Docker 가 컨테이너를 따로 올려 순서가 보장되지 않는다.
*   **응답기를 다시 띄우기 전에 거부 목록 파일이 있는지 본다.** 까닭은 아래
    「한계」에 있다.

근거는 설계 r1.7.4 3-6 · 3-8, 명령은 RUNBOOK 의 「운영 순서」 절이다.

## 긴급 절단과 해제

**거부 목록**은 `${DEMO_HOME}/ingest-auth/deny/deny-tokens` 파일이다. 한 줄에
토큰 하나, `#` 뒤는 주석이다. 응답기는 publish 인증마다 이 파일을 다시 읽고,
한 번 읽은 토큰은 떠 있는 동안 지우지 않는다(합집합[^union]).

**긴급 절단** — 어떤 토큰의 송출을 지금 끊고 다시 붙지 못하게 한다.

1.  거부 목록에 그 토큰 한 줄을 덧붙인다. 덧붙이기 전에 값이 토큰 꼴인지 보는
    검사와 덧붙이기가 한 명령이다. 꼴이 아닌 줄(틀린 줄)은 판정에서 건너뛰지만
    healthcheck 를 실패시키기 때문이다. 효과는 곧바로 난다.
1.  그다음 `ingest-auth cut <토큰>` 으로 지금 붙어 있는 그 토큰의 연결을 끊고
    끊겼는지 확인한다. 순서(쓰기 → cut)를 바꾸지 않는다.
1.  종료 코드 0 은 완료, 1 은 미완(출력의 사유별 대응은 RUNBOOK), 2 는 시작하지
    않음(거부 목록에 그 토큰이 없음 등 — 끊은 것 없음)이다.

**해제** — 원인이 풀렸고 키가 새지 않은 토큰을 다시 허용한다.

1.  지우기 전 사본을 두고, 대상 토큰의 줄을 모두 뺀 새 파일을 다른 이름으로
    만든다. 살아 있는 파일은 승인 전까지 바꾸지 않는다.
1.  새 파일이 사본에서 대상 하나만 빠졌는지 단언하고, 절단 사유 주석을 붙인 뒤
    다시 단언한다.
1.  비유출 판정 · 원인 해소 확인 · kty 승인.
1.  살아 있는 파일이 사본과 같은지 다시 보고 새 파일을 이름 바꾸기로 끼운 뒤
    **응답기만** 다시 시작한다. MediaMTX 는 건드리지 않는다.
1.  healthy 와 동작(대상 허용 · 남은 토큰 거부 · 다른 송출 유지)을 본다. 남은
    토큰이 허용되거나 healthy 시한을 넘기면 사본 되돌림(준비 · 적용)으로 돌아간다
    — 지우기 전 사본에 **그사이 덧붙은 긴급 절단 줄을 옮겨 붙인** 파일을 끼운다.
    사본을 그대로 끼우면 그 절단이 재시작 때 조용히 풀린다. 대상이 허용되지
    않으면(차단이 유지된 쪽) 원인을 본다. 적용이 새 파일을 끼운 뒤 응답기를 다시
    시작하기 전에 끊겼으면 응답기만 다시 시작한다 — 준비부터 다시 하면 대상이
    사본에 없어 막힌다. 그 밖이면 준비부터 다시 한다. MediaMTX 까지 다시
    시작됐으면 명령 꼴을 고친다.

*   합집합이라 줄을 지워도 응답기를 다시 시작하기 전에는 풀리지 않는다.
*   다시 시작하는 동안 응답기가 멈췄다 다시 듣기까지의 짧은 구간에는 모든 계정의
    새 연결 · 재접속이 거부된다(로컬 실측 — 멈춤 → 시작 0.2–0.3초, 첫 정상
    수락까지 1.2–3.3초. healthy 판정을 기다리는 창 전체가 아니다). 상자의 값(멈춤
    → 시작 0.86초 · 첫 정상 수락까지 4.06초 · 창 31초)과 창이 상자에서 긴 까닭은
    RUNBOOK 「해제」 절의 동작 확인에 있다. 지금은 서비스 사용자가 없어 따로
    알리지 않는다.
*   긴급 절단은 해제를 기다리지 않는다. 해제를 준비하는 동안 절단이 끼면 적용
    직전의 재확인이 멈추고, 준비부터 다시 한다.
*   거부 목록에 틀린 줄이 생기면 손으로 고치지 않고 RUNBOOK 의 「틀린 줄 걷기」로
    걷는다(응답기 재시작 없음).

단계별 명령 · 단언 · 실패 갈래는 RUNBOOK 의 「긴급 절단」 · 「해제」 절이
정본이다. 근거는 설계 r1.7.4 3-4 · 8-2 16 이다.

## 한계

*   **유출 키는 해제하지 않는다.** 키가 샜거나 판단할 수 없을 때도 차단을
    유지한다. 새 키를 주는 화면이나 운영자용 수단이 없다 — 사용자 JWT 를 받는
    `rotate` API 만 있다. 웹 「재발급」은 같은 키를 주므로 회복 수단이 아니다. 그
    수단은 따로 정한다(설계 r1.7.4 3-4 4 · 8-2 16).
*   **거부 목록 파일이 없으면 빈 목록이다.** 응답기가 떠 있는 동안은 읽은 토큰을
    합집합으로 기억해, 파일을 지워도 차단이 유지된다. 그러나 응답기가 다시 뜨면
    파일부터 다시 쌓는다. 그래서 파일만 지워진 채 자동 재시작(컨테이너 재시작 ·
    상자 재부팅)되면 거부했던 토큰이 신호 없이 다시 붙는다. 흔적은 응답기 로그의
    `publish_allowed` 한 줄뿐이다. 디렉터리째 없으면 `compose.yml` 의 긴 꼴
    bind(`create_host_path: false`)로 응답기 기동이 실패한다. 그래서 응답기를 다시
    띄우기 전에 거부 목록 파일이 있는지 본다(RUNBOOK 「운영 순서」 — kty 106차).
*   **auth 장애 뒤 회복이 늦어질 수 있다.** 끊긴 뒤 300초 안(5초 재시도 간격
    구간)이면 송출 하나는 약 9초, 여럿이면 약 10–18초, 최악 약 22초에 다시
    붙는다(계산). 22초는 차례를 먼저 가진 거절 토큰 · 계속 실패하는 토큰이 없고
    첫 재확인이 시한 안일 때다. 거절 토큰은 하나마다 약 8초를 더하고, 계속
    실패하는 토큰이 p 개면 최악 18 + 8p + 8⌈(p − 1)/2⌉초(p = 2 면 약 42초)다
    (RUNBOOK 「운영 순서」의 로그 읽기). 장애가 5분을 넘어 30 · 60초 간격 구간에
    들고, 계속 실패하는 키가 정상 키보다 먼저 오면 정상 키는 약 333초(30초
    간격) · 363초(60초 간격)까지 거절될 수 있다(계산 — 설계 r1.7.4 8-2 15).
*   **「양보 사슬」 — 정상 토큰의 재확인이 약 5분 밀릴 수 있다.** auth 장애 중
    보안 그룹 안쪽 상대가 토큰 꼴 가짜 이름 여럿(모의 9개)을 기억시키면, 회복 뒤
    정상 토큰은 차례를 양보하느라 그 기억이 풀릴 때(마지막 판정 불가 뒤 300초 +
    한 주기 — 모의 303.8초)까지 거절될 수 있다. 상한은 그 300초로 선다. 차례 돌림
    (가장 오래 기다린 토큰부터)은 재시도 간격이 10초보다 짧은 구간에서만 서고,
    30 · 60초 간격 구간에서는 먼저 온 순서다. 규칙은 그대로 두고 한계로 적는다
    (kty 101차).
*   **MediaMTX 커널 값은 조정하지 않는다.** 큰 cut 직후나 토큰 꼴 송출 시도가
    몰리면 MediaMTX 쪽 임시 포트가 모자라 cut 이 `api_auth` 로 실패할 수 있다.
    그 갈래의 처방은 RUNBOOK 의 「긴급 절단」 절에 있다(kty 106차).
*   **큰 cut 은 모든 계정의 새 송출을 잠깐 막을 수 있다(참고 — 미교정).** cut 의
    kick 하나하나가 Control API 인증 요청으로 응답기의 처리 시간 예산을 쓴다. 한
    토큰의 kick 이 약 4,800개를 넘으면(그 토큰의 허용 연결 기록 줄이 그만큼 많을
    때) 예산이 바닥나, 모든 계정의 새 송출이 십여 초(기록이 가득 찬 17,339줄이면
    약 14초) `budget_exhausted` 로 거부될 수 있다. 차감을 상한으로 가정한 호스트
    단위 시험의 계산이고, 실제 응답기 몫은 재지 않았다(판정불가). 우리 규모(kick
    1,700개까지)에서는 생기지 않았다.
